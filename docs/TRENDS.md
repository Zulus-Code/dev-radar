# Механика трендов (Фаза 3)

Как Dev Radar считает «растущие» репозитории. Это спецификация: реализация должна ей
соответствовать, а расхождения — исправляться здесь, а не молча в коде.

## 1. Проблема

У GitHub нет API трендов. Запрос `pushed:>7d sort=stars` возвращает популярное, а не растущее:
топ выдачи — одни и те же гиганты. Публичные trending-API мертвы, `github.com/trending`
не отдаёт CORS.

Единственный честный сигнал — **прирост звёзд**. Значит нужно самим хранить историю:
снимать число звёзд и сравнивать снимки между собой.

## 2. Что храним

SQLite-файл в каталоге данных приложения (`app_data_dir()/dev-radar.db`).

```sql
CREATE TABLE repos (
  id            INTEGER PRIMARY KEY,   -- GitHub repo id, стабилен при переименовании
  full_name     TEXT NOT NULL,
  language      TEXT,
  stars         INTEGER NOT NULL,
  forks         INTEGER NOT NULL,
  open_issues   INTEGER NOT NULL,
  source        TEXT NOT NULL,         -- 'seen' | 'top'
  first_seen    TEXT NOT NULL,         -- ISO date
  last_seen     TEXT NOT NULL,         -- ISO date
  missing_since TEXT                   -- ISO date, если API отдал 404/410
);

CREATE TABLE snapshots (
  repo_id     INTEGER NOT NULL,
  day         TEXT NOT NULL,           -- 'YYYY-MM-DD', UTC
  stars       INTEGER NOT NULL,
  forks       INTEGER NOT NULL,
  open_issues INTEGER NOT NULL,
  PRIMARY KEY (repo_id, day)
);
CREATE INDEX idx_snapshots_day ON snapshots(day);

CREATE TABLE meta (
  key   TEXT PRIMARY KEY,              -- 'last_sync_at', 'schema_version'
  value TEXT NOT NULL
);
```

Одна строка `snapshots` на репозиторий в сутки: повторный снимок за тот же день
перезаписывает предыдущий (`INSERT OR REPLACE`). Внутридневная история не нужна —
дельта считается по дням.

## 3. Кого отслеживаем

Список трекинга — объединение:

1. **`seen`** — всё, что попадало в выдачу приложения за последние 30 дней;
2. **`top`** — топ-300 по фильтрам по умолчанию, добирается при каждом синке;
3. уже отслеживаемые репозитории (чтобы не терять историю).

Потолок — **2 000 репозиториев**. При переполнении выкидываются самые давние `seen`;
`top` не выкидывается никогда.

Почему так: `seen` делает тренды релевантными тому, что пользователь ищет, `top` даёт
стабильный фон, а потолок держит базу и синк в разумных размерах.

## 4. Когда снимаем

- **При запуске приложения**, если `meta.last_sync_at` старше **6 часов**. Отдельного
  демона нет: приложение не запущено — снимков нет.
- Один батч — **50 репозиториев** через GraphQL `nodes(ids: [...])` за запрос.
  2 000 репозиториев = 40 запросов, это ~40 points из 5 000/час.
- Ошибки:
  - `404`/`410` → пишем `missing_since`, репозиторий выпадает из трендов, но история остаётся;
  - исчерпан rate limit → синк прерывается, `last_sync_at` **не** обновляется, повтор при
    следующем запуске (не раньше чем через 6 часов);
  - сеть недоступна → то же самое, тихо, без модалок.
- После успешного синка: `last_sync_at = now`, чистка `snapshots` старше **180 дней**.

**Требуется PAT.** Без токена GraphQL недоступен, а REST не тянет 2 000 репозиториев
(10 запросов/мин анонимно). Без токена синк не запускается; UI показывает подсказку
«для трендов нужен Personal Access Token».

## 5. Как считаем дельту

Целевое окно — 7 дней. Берём самый свежий снимок и ближайший снимок не позже `today − 7`.

```
delta_7d = stars(latest) − stars(snapshot, ближайший к today−7)
```

Если снимка семидневной давности нет, окно понижается:

| Доступная история | Окно       | Подпись в UI        |
|-------------------|------------|---------------------|
| ≥ 7 дней          | 7 дней     | «за неделю»         |
| 1–6 дней          | весь период| «за N дн.»          |
| < 1 дня           | нет дельты | «—», в конце списка |

Дельта может быть отрицательной (звёзды теряют) — это нормально, показываем как есть.

SQL для списка:

```sql
SELECT r.*, s.stars AS stars_now,
       s.stars - COALESCE((
         SELECT s2.stars FROM snapshots s2
         WHERE s2.repo_id = r.id AND s2.day <= date('now', '-7 day')
         ORDER BY s2.day DESC LIMIT 1
       ), s.stars) AS delta_7d
FROM repos r
JOIN snapshots s ON s.repo_id = r.id
WHERE s.day = (SELECT MAX(day) FROM snapshots)
```

## 6. Что видит пользователь

- Сортировка **«Растущие»** — по дельте, с честной подписью окна («за неделю» / «за 3 дн.»).
- Бейдж на карточке: `+412★/нед` или `+38★/сут`; у репозиториев без истории — `—`.
- Настройки → «Сбор статистики»:
  - вкл/выкл (выключено — синк не запускается, старые снимки остаются);
  - «Отслеживается N репозиториев»;
  - «Последнее обновление: …».
- Первый запуск: снапшот-база пустая, дельт нет. Через 6 часов появляется окно «за сутки»,
  через 7 дней — полноценное недельное.

## 7. Ограничения, которые принимаем осознанно

1. **Историю задним числом не засеять.** `GET /repos/{o}/{r}/stargazers` отдаёт по 100 звёзд
   на страницу: для репозитория с 400k звёзд это 4 000 запросов. Не делаем.
2. **Приложение не запущено — данных нет.** Пропущенные дни просто отсутствуют, окно
   расширяется до последнего доступного снимка.
3. **Тренд — это дельта звёзд, а не «качество».** Накачка звёзд и боты видны как рост;
   фильтровать не пытаемся.
4. **Хранение — 180 дней.** 2 000 репозиториев × 180 дней ≈ 360 тыс. строк ≈ 15–20 МБ.
   Этого хватает для окон 1/7/30/90 дней.

## 8. Поток целиком

```
старт приложения
   └─ last_sync_at старше 6 ч?
        ├─ нет → выходим
        └─ да
            ├─ собрать трекинг: seen(30 дн.) ∪ top-300 ∪ уже известные, потолок 2000
            ├─ GraphQL nodes(ids) пачками по 50
            │     ├─ 404/410 → missing_since
            │     └─ ok → INSERT OR REPLACE snapshots(today)
            ├─ удалить snapshots старше 180 дней
            └─ last_sync_at = now

UI (главная)
   ├─ сортировка «Растущие» → SQL delta (7 дн., иначе весь доступный период)
   ├─ бейдж +N★/нед на карточке
   └─ настройки → статус сбора, кол-во отслеживаемых, последний синк
```
